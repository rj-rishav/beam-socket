# 0.3.0 Performance Phase — Task 3a: Lazy Codec Read Buffer (rejected)

> **Invalidated measurement (2026-09-30):** every `throughput16k` number below
> was taken while the bench server's default 64 KiB `Disconnect` budget closed
> all 8 echo clients with 1013 within about a second, and the driver counted lost
> replies. The gate compared how fast connections died, not codec throughput.
> The rejection is therefore unproven either way; see `benchmarks/README.md`
> and the re-test in `docs/reports/0.2.1-hardening.md`.

**What this is:** the before/after measurement for `docs/plans/0.3.0-performance.md`
Task 3a — shrinking tungstenite's codec read-buffer chunk
(`crates/core/src/transport/websocket.rs`, `READ_BUFFER_SIZE`) from 4 KiB to
1 KiB for an idle-memory win. **Outcome: rejected.** The change buys a real
~25-30% per-connection memory reduction but costs 20-35% echo throughput on
large (16 KiB) frames, breaching the plan's explicit gate ("any regression >
10% on the big payload kills the change — revert, document, move on"). No
code shipped; `READ_BUFFER_SIZE` stays at `4 * 1024`.

This corrects an earlier read of the same idea. A first pass (same session,
see `docs/reports/0.3.0-task3a-pm-brief.md` for the full draft) measured one
"before" run against three "after" runs and saw the 16 KiB throughput
number move from 887 to ~2,140-2,907 msg/s — an apparent 2-3x win. Re-running
at the plan's actual harness scale (`--memConns 10000 --memSettleMs 8000`,
7-9 runs per side instead of 1-3) shows that 887 was the outlier, not the
after-side numbers: the honest before/after gap runs the other way.

## The change (what was tried)

```rust
const READ_BUFFER_SIZE: usize = 1024; // was 4 * 1024
```

tungstenite 0.29's `ReadBuffer<const CHUNK_SIZE>` pre-allocates a
`Box<[u8; CHUNK_SIZE]>` at construction that lives for the connection's
lifetime — shrinking it directly cuts per-connection heap footprint. That
part of the theory holds (see the memory numbers below). What it costs:
`CHUNK_SIZE` is also the per-read scratch space, so a payload bigger than
the chunk takes multiple `read_from` calls to fill — a 16 KiB frame needs
~16 calls at a 1 KiB chunk vs. ~4 at 4 KiB. That's roughly 4x the read-loop
iterations (syscall + bookkeeping overhead each) per large frame, which is
exactly the mechanism behind the throughput regression measured below.

Also landed alongside the code change (kept regardless of the revert — this
is what caught the regression): `benchmarks/driver.mjs`'s `measureThroughput`
now accepts a `payload` argument, and `main()` runs it twice — once at the
existing 64 B baseline (`result.throughput`, unchanged field) and once at a
new 16 KiB payload (`result.throughput16k`). This is Task 3a's DoD-mandated
large-frame regression gate, and it's staying in the harness for any future
attempt at this lever.

## Method

**Read this first — same rules as `benchmarks/REPORT.md` and
`docs/reports/0.3.0-task1-flush.md`:** shared, contended sandbox, not the
pinned reference box. This specific metric (16 KiB throughput, 8 pipelined
connections, 3 s window) turned out to have much wider run-to-run spread
than anything else in this suite — up to 4.8x between runs of the *same*
code state (767-3,667 msg/s) — which is exactly why the first-pass 1-vs-3
sample size produced a wrong-direction reading. Every number below is
7-9 same-box, same-session runs per state, all individual runs shown so you
can judge signal vs. noise yourself, not the 1-3 the first pass used.

Both states built from the same source tree, same session: "before" is
`crates/core/src/transport/websocket.rs` stashed to its pre-change form
(`READ_BUFFER_SIZE = 4 * 1024`), "after" is the tried change
(`= 1024`); `cargo build -p beamsocket-node --release --features napi` +
`copy-native.mjs` between states. `benchmarks/driver.mjs` (with the
`throughput16k` addition) unmodified between the two. Memory measured at
the plan's Task 2 harness settings, `--memConns 10000 --memSettleMs 8000`
(the PM brief's first pass used `--memConns 5000 --memSettleMs 4000`,
below the stability floor Task 2 established — included below as context
only, not part of the gate verdict).

## Results — proper-harness re-measurement (the gate-deciding numbers)

`--memConns 10000 --memSettleMs 8000`, 7 before-runs / 6 after-runs (the
memory/fan-out fields; throughput/latency use the full before=8/after=9
pool below since those don't depend on `memConns`).

**Every cut of the data — with or without the PM's original outlier sample,
with or without the one clearly box-contended "after" run (r3: p50 spiked
to 3.5 ms and 64 B throughput dropped to 56k on that same run, both
consistent with general box contention, not a 16-KiB-specific effect) —
shows a regression past the plan's 10% line.** This isn't noise resolving
in the change's favor at higher N; it's the opposite of the first-pass
read. The mechanism (4x more `read_from` calls per large frame) is a
plausible, direct explanation, unlike the first pass's "less buffer
housekeeping" theory, which doesn't predict a slowdown from more/smaller
reads.

The PM's first-pass "before" sample (887) sits far below the 2,547-3,667
cluster every other before-run lands in — an isolated low reading, not
the population's center. Comparing it to three after-runs that happened to
land on the higher side of the after distribution (2,140-2,907) produced
the apparent 2-3x win; it doesn't survive n=8 vs n=9.

## Verdict

| Gate (from `docs/plans/0.3.0-performance.md` Task 3a) | Result |
|---|---|
| Idle-memory win, measured on the fixed (Task 2) harness | ✅ Pass — real, ~27% per-conn reduction |
| `latency.p50ms` doesn't regress > 10% | ✅ Pass — +3.6%, within noise |
| `throughput.msgsPerSec` (64 B) within ±10% | ✅ Pass — −6.1% |
| **16 KiB throughput: any regression > 10% kills the change** | ❌ **Fail — −21% to −46% depending on cut, consistent in direction across every cut of the data** |

**Decision: reverted.** `READ_BUFFER_SIZE` stays at `4 * 1024`
(`crates/core/src/transport/websocket.rs`). This is the plan's own
pre-written response to this exact scenario — "revert, document, move
on" — not a new judgment call. The memory win doesn't buy back a ~20%+ hit
on any workload that moves frames near or above 1 KiB (file transfers,
larger JSON payloads, batched events), and BeamSocket's own architecture
doc (`ARCHITECTURE.md` §5) frames the read-buffer size as tunable precisely
*because* it trades density against large-frame cost — this measurement is
that trade-off resolving the wrong way at 1 KiB.

What ships from this session: the `benchmarks/driver.mjs` 16 KiB throughput
gate itself (now a permanent large-frame regression check for any future
attempt at this or a related lever), and this report as the documented
negative result — the repo's benchmark-honesty rule from
`benchmarks/README.md` applies to rejected changes, not just shipped ones.

A future attempt at this lever should look at the plan's other suggestion —
true allocate-on-first-frame laziness (holding the config until the first
read) rather than a flat smaller chunk — which wouldn't pay the large-frame
tax on every read once a connection is actually receiving big frames. Not
attempted here; out of scope for a single-lever revert-and-document task.
