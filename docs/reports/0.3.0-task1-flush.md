# 0.3.0 Performance Phase — Task 1: Adaptive Bridge Flush

**What this is:** the before/after measurement for `docs/plans/0.3.0-performance.md`
Task 1 — the adaptive-flush change to `crates/node/src/bridge.rs`'s
`drain_loop`. Also folds in Task 2 (idle-RSS harness fix, a prerequisite so
the memory numbers below are trustworthy) and the Task 5 `remote_except`
Rust-level test, both landed the same session.

**Read this first — same rules as `benchmarks/REPORT.md`:** shared, contended
sandbox, not the pinned reference box; run-to-run variance on this class of
machine is documented at ~10–20%, sometimes more. Every number below is a
mean of 3 same-box, same-hour runs unless stated otherwise, and the per-run
spread is shown so you can judge signal vs. noise yourself.

## The change

`drain_loop` (the Rust→JS event bridge, RFC 0001 design C) used to always
wait up to `BRIDGE_FLUSH_INTERVAL` (1 ms) for a batch to fill before flushing
a partial one. At low concurrency — one echo in flight, nothing to batch
with — that 1 ms was pure added latency, paid on every single message.

The fix: after the first event of a batch arrives, greedily drain whatever's
**already queued** with `try_recv()` (no waiting). If the queue runs dry and
the batch is still small (< `LOW_LOAD_THRESHOLD = 16`), flush immediately —
skip the timer entirely. Under real load the greedy drain already pushes the
batch past that threshold before the check ever runs, so the existing
timer+select fill loop is untouched and still governs batching once there's
real concurrency. `BRIDGE_BATCH`, `BRIDGE_FLUSH_INTERVAL`, and the queue
capacities — all RFC-0001-validated — are unchanged.

## Method

Both states built from the same source tree on this box, same session, same
hour: the "before" addon is this branch with `crates/node/src/bridge.rs`
stashed back to its pre-change form (`cargo build --release --features napi`
+ `copy-native.mjs`, same as the "after" build); the "after" addon is the
committed change. `benchmarks/driver.mjs`, unmodified between the two runs.
3 full passes per state, Node v22.23.2, `beamsocket` server adapter
(`io.toRoom('bench').send()` fan-out, single-node — no cluster config
involved in this change or this measurement).

## Results — echo (8 pipelined connections, 64 B payload)

| Metric | Before (avg) | Before (runs) | After (avg) | After (runs) | Δ |
|---|---|---|---|---|---|
| Throughput | 77,122 msg/s | 72407, 79760, 79200 | **145,942 msg/s** | 151387, 153707, 132733 | **+89.2%** |
| p50 latency | 2.193 ms | 2.164, 2.206, 2.208 | **1.025 ms** | 0.937, 1.050, 1.087 | **−53.3%** |
| p99 latency | 3.365 ms | 3.192, 3.228, 3.675 | 3.419 ms | 3.585, 3.501, 3.170 | +1.6% (noise) |

**p50 moved by 1.17 ms — more than the entire 1 ms `BRIDGE_FLUSH_INTERVAL`
this change targets.** That's the headline: the flush-timer wait really was
most of the low-concurrency latency tax, and removing it at low load roughly
doubled round-trip throughput on this 8-connection pipelined suite too (more
round trips fit in the same window once each one isn't paying a ~1 ms tax).

p99 is flat — expected. The timer wait was a low-load-specific cost; p99 on
a shared, contended box is dominated by scheduler/CPU noise the flush change
was never going to touch.

## Results — fan-out completion (512 B payload, best-of-5 median)

| Room size | Before (avg) | Before (runs) | After (avg) | After (runs) | Δ |
|---|---|---|---|---|---|
| 1,000 | 15.17 ms | 14.50, 14.90, 16.11 | **9.81 ms** | 11.79, 7.57, 10.08 | **−35.3%** |
| 3,000 | 29.83 ms | 29.52, 29.77, 30.19 | 33.27 ms | 39.11, 32.01, 28.69 | +11.5% (inside noise) |
| 5,000 | 42.53 ms | 41.61, 42.52, 43.47 | 42.20 ms | 41.73, 42.99, 41.89 | −0.8% |

1k improved by the same mechanism as echo latency — a small room's fan-out
events also arrive as a short burst that benefits from skipping the timer.
3k's "after" spread (28.69–39.11 ms) already covers the entire gap between
the before and after averages — this reads as box noise, not a regression;
call it a wash pending a cleaner run. 5k is flat, as expected: at that size
the burst of events already blows past `LOW_LOAD_THRESHOLD` on the first
greedy drain, so the new code path never fires there — behavior is
unchanged by construction, and the measurement confirms it.

## Where this leaves BeamSocket vs. the competition

Same-box competitor numbers (ws 8.21.1, uWebSockets.js 20.49.0, Socket.IO
4.8.3) are carried over from the 2026-08-20 same-session run — those
libraries weren't touched today, so re-running them wasn't necessary; see
`benchmarks/results/{ws,uws,socketio}-thisbox*.json`.

| Library | Throughput | p50 | p99 | Fan 1k | Fan 3k | Fan 5k |
|---|---|---|---|---|---|---|
| **BeamSocket (after)** | 145,942 | 1.025 | 3.419 | **9.81** | 33.27 | 42.20 |
| BeamSocket (before) | 77,122 | 2.193 | 3.365 | 15.17 | 29.83 | 42.53 |
| ws 8.21.1 | 211,830 | 0.927 | 2.175 | 15.04 | 25.52 | 38.63 |
| uWebSockets.js 20.49.0 | 212,494 | 0.956 | 3.597 | 10.77 | 22.73 | 33.65 |
| Socket.IO 4.8.3 | 61,323 | 2.778 | 8.599 | 24.38 | 65.53 | 122.56 |

- **The gap to ws/uWS on raw echo nearly closed.** Throughput gap: 2.75×
  before → 1.45× after. p50 gap: ~2.3× before → ~1.1× after — BeamSocket's
  p50 is now within noise of the raw-transport libraries at this scale,
  which was not true this morning.
- **BeamSocket now wins 1k-member fan-out outright** — 9.81 ms vs. ws's
  15.04 ms and uWS's 10.77 ms. That's new; before this change BeamSocket
  trailed both at every size in this suite.
- **The Socket.IO lead widened further** — was ~1.3× on throughput, now
  ~2.4×; p50 gap went from ~1.3× to ~2.7×.
- 3k/5k fan-out standing is unchanged (still behind ws/uWS there) — this
  change doesn't touch the mechanism that would close that gap (see
  `docs/plans/0.3.0-performance.md` Tasks 3/4).

## Idle memory (Task 2's fixed harness — context, not this task's target)

`bytesPerConn` is unaffected by the flush change, as expected — `drain_loop`
doesn't touch per-connection allocation. Before avg 5,996 B/conn (3 runs:
5209, 6573, 6206), after avg 4,974 B/conn (3 runs: 4635, 4619, 5669) — both
inside the ±25% run-to-run band the fixed harness (Task 2) now produces; no
claim of a memory-side effect either way.
