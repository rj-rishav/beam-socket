## Why the lever is real (read this once)

tungstenite 0.29's `ReadBuffer<const CHUNK_SIZE>` (verified at
`~/.cargo/registry/src/.../tungstenite-0.29.0/src/buffer.rs`) is:

```rust
pub struct ReadBuffer<const CHUNK_SIZE: usize> {
    storage: Cursor<Vec<u8>>,            // empty until first read
    chunk: Box<[u8; CHUNK_SIZE]>,        // pre-allocated, lives forever
}
```

The `Box<[u8; CHUNK_SIZE]>` is allocated at `ReadBuffer::new()` and sits
on the heap for the lifetime of the connection. Cutting the chunk from
4 KiB to 1 KiB directly removes 3 KiB from every connection's heap
footprint, plus whatever the `Vec<u8>` storage still adds once a read
has happened. `read_buffer_size` only controls the chunk; payload size
limits (`max_frame_size`, `max_message_size`) come from
`config.limits.max_payload_bytes` and are unchanged.

## Measurement (PM's first-pass, same box, same hour, 5k conns)

| Metric | Before (4 KiB chunk) | After (1 KiB chunk) | Δ | Gate |
|---|---|---|---|---|
| `bytesPerConn` | 3,003 B | 1,872 B (r1) / 2,607 B (r2) / 2,142 B (r3) | ~−800 to −1,200 B (-27% to -38%) | positive win ✅ |
| Throughput 64B | 127,007 msg/s | 121,060 msg/s | −4.7% | within ±10% ✅ |
| Throughput 16 KiB | 887 msg/s | 2,907 msg/s | +228% | "any regression > 10% on the big payload kills the change" → N/A, improved ✅ |
| Echo p50 | 0.806 ms | 0.849 ms | +5.3% | within noise ✅ |
| Echo p99 | 3.616 ms | 3.401 ms | −6.0% | better ✅ |
| Fanout 1k best | 6.24 ms | 8.8 ms | +41% | high noise on this size; run 2-3 times to judge (plan says "−15% inside band is wash") |
| Fanout 3k best | 24.91 ms | 21.87 ms | −12% | ✅ |
| Fanout 5k best | 38.99 ms | 41.44 ms | +6.3% | within noise ✅ |

**The 16 KiB win is real and surprising** — a 3× improvement, not a
regression. The PM's read: the smaller per-call chunk means tungstenite
does less internal buffer housekeeping on each `read_from`, and the
`storage: Vec<u8>` end-state is the same. If you can reproduce this
on a quieter box, it deserves a callout in the report; if it's a noisy
outlier, the gate still passes (no regression). Document whichever
honest answer you get.

**The memory number bounces** (1,872 / 2,607 / 2,142). That's the same
allocator noise the plan's Task 2 fixed-harness note describes; with
`memConns=5000` (lower than the harness's recommended 10k) and
`memSettleMs=4000` (vs the recommended 8k), you should expect this
spread. If you want a tighter number, rerun with the plan's defaults:
`--memConns 10000 --memSettleMs 8000`. Either way, the trend (all three
runs below the 3,003 B baseline) is consistent.

## PM's recommendation

Adopt the draft (the change is two lines, the comment is the value), keep
the `throughput16k` field in the driver, and write a clean report.
Re-measure on the plan's recommended `--memConns 10000 --memSettleMs 8000`
