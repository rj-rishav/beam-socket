# 0.2.1 hardening: tested theories and outcomes

Branch `perf/0.2.1-hardening`, 2026-09-30. Rule for this work: every theory
was reproduced or measured *before* code changed, and each fix ships with the
test or measurement that proved it. Machine: Intel i5-1135G7, Linux
7.0.0-31-generic, Node 24.15.0, no CPU pinning. These are local results; the
pinned-box release gates are still required before publishing.

## 1. Relayed `toSocket` and the `Disconnect` policy

`cluster.rs` delivered remote `toSocket` with a bare `mailbox.push` and ignored
the outcome. On a `Disconnect` overflow the mailbox closes itself, but only the
caller can signal the close. Without the signal, the writer drains and exits
while the reader keeps running: a half-dead connection that later reports 1006,
not 1013. The new `relayed_socket_send_honours_disconnect_policy` test failed
(`close must be signalled`) before the fix.

Fix: `ConnHandle::push` enforces the policy, and local send, fan-out and relay
all use it. No bare `mailbox.push` call sites remain outside it.

## 2. Empty frames and the mailbox budget

The budget was payload bytes only, so a zero-length frame cost 0 and could
never trigger backpressure. The new test pushed 10,000 empty frames into a
64-byte mailbox, and all 10,000 were queued under every policy. Each frame is
now charged `max(len, 1)`, so the entry count is bounded by the HWM. Before
the fix, 1-byte frames already had that worst case. Non-empty frames are
unaffected.

## 3. Benchmark validity: the 16 KiB throughput was measuring dead sockets

First test (64 B, `ws` and BeamSocket): counted equals arrived equals sent. The
reported total was **not** inflated. One reply does resolve every outstanding
`once` listener, but every send is eventually answered, so totals match. The
real defect was the window: in-flight reached 4,838 against `ws` (cap 160) and
about 340 against BeamSocket, so each library ran under a different load.

Second test (16 KiB) exposed a larger problem. BeamSocket replies were lost:
9,080 sent, 1,753 arrived, 8,920 counted (5.09× overcount). Server metrics
showed `backpressureDrops: 8`, `bridgeDropped: 0`, and every client closed
with **1013**. The bench server used the default 64 KiB `Disconnect` budget
while `ws` buffers without limit and `uws` sets `maxBackpressure: 0`. Twenty
pipelined 16 KiB echoes (320 KiB) per client exceed it.

| BeamSocket HWM | 16 KiB echoes in 3 s | Disconnects |
|---|---:|---:|
| 64 KiB (default) | 8,092 | 8 / 8 clients |
| 512 KiB | 63,821 | 0 |
| 4 MiB | 63,627 | 0 |
| `ws` (unbounded) | 70,431 | 0 |

Fixes: FIFO echo correlation in `driver.mjs` (raw and Socket.IO), and the
BeamSocket bench server uses a 16 MiB HWM to match the other servers. Re-run
(3×): 16 KiB `ws` ≈ 22k/s vs BeamSocket ≈ 21k/s; 64 B `ws` ≈ 195k/s vs
BeamSocket ≈ 136k/s. Every earlier BeamSocket `throughput16k` number,
including Task 3a's gate, is void. uWS.js could not be re-run locally: it does
not support Node 24.

The 64 KiB `Disconnect` product default is unchanged. It is a deliberate
slow-consumer policy, but apps that pipeline large frames need a larger
`highWaterMark`. This is a documentation and product decision, not a bug fix.

## 4. Read buffer 4 KiB → 1 KiB, re-tested

Two native builds that differ only in `READ_BUFFER_SIZE` were swapped under the
fixed driver. Ten rounds, alternating order, used the full harness (10k-conn
memory, 1k fan-out). Raw JSON: `benchmarks/results/readbuffer-retest/`. The
values are paired per-round deltas (1 KiB vs 4 KiB):

| Metric | 4 KiB median | 1 KiB median | Paired Δ median | Per-round range |
|---|---:|---:|---:|---|
| Idle bytes/conn | 9,597 | 7,376 | **−23.3%** | −17.1% … −29.3% (10/10) |
| 16 KiB echo/s | 22,172 | 21,391 | −2.0% | −14.0% … +10.9% |
| 64 B echo/s | 149,417 | 138,313 | −0.7% | −22.4% … +15.9% |
| p50 latency | 0.676 ms | 0.637 ms | −1.8% | noisy |
| 1k fan-out | 12.0 ms | 11.7 ms | −3.9% | noisy |

The memory gain is consistent in every round. The 16 KiB cost is small and
well inside the 10% gate, but this laptop varies ±10–15% per run: one round
was −14% and another +10.9%. Confirm on the pinned box before release.

## Follow-ups (not done here)

- **Mesh `:0` bind flake.** `MeshNode` binds UDP on `:0`, then TCP on the same
  port. On a machine with about 9k TIME_WAIT sockets (right after the memory
  harness), three `phase3d` tests failed with `AddrInUse`. They pass once
  TIME_WAIT drains. Retrying the pair on `AddrInUse` when the port was 0 would
  de-flake tests and CI. Fixed-port production configs are unaffected.
- The 64 B echo gap vs `ws` (~70%) is the next performance target. The
  untested hypothesis is the JS-handler round trip (bridge → TSFN → `send`
  FFI); profile it before changing anything.
- Clustered presence/user-query IDs and admin-disconnect node scoping still
  need the correctness review named in the exclusions report.
