# PR: 0.2.0 — Clustering Reaches JavaScript

**Milestone:** 0.2.0 (ENGINEERING.md §14; work order "BeamSocket 0.2.0 —
Clustering Reaches JavaScript"). Branch: `v0.2.0-cluster-js`, from `master`.
This is the milestone the Phase 3D PR notes deferred: "JS-level cluster
activation is config-surface + codec, not yet wired through the addon." Core
(`crates/core`) has carried the full mesh boot/relay/stats path since 3D —
`Engine::start` already spawns the mesh, `cluster_summary()` /
`cluster_peer_pressures()` / `send_node()` already exist. This PR is the addon
+ SDK wiring that makes it reachable from `new BeamSocket({ cluster: {...} })`.

## Fixed: cross-node `except` was a no-op

Found while tracing the required "`except` honored across nodes" test through
the real `Engine` API (not the 3D gate test's hand-rolled replica — see below).

`Engine::broadcast_room`'s `except: &[ConnectionId]` has no way to name a
foreign node. The existing relay path (`node_excepts(c.node_id(), except)`)
stamps **every** excepted connection with the **sending** node's own id. The
receiving peer's `excepts_for` filter only keeps entries tagged with **its
own** node id. Sender id ≠ any peer's id, by construction — so a cross-node
except could never match on the receiving side. It silently did nothing.

The 3D gate test that claims to cover this
(`phase3d.rs::e2e_every_verb_reaches_remote_exactly_once_except_honored`)
passes anyway, because it doesn't call `Engine::broadcast_room` — it calls a
hand-rolled test replica (`Node::to_room`) that builds correctly-tagged
`NodeConnId { node: 3, local: m3 }` excepts directly and hands them straight
to `Cluster::relay_room`, bypassing the real `Engine` facade entirely. The
mesh/relay layer has always been able to honor a cross-node except; the
`Engine` facade JS actually goes through could not produce one.

**Fix:** `broadcast_room`/`broadcast_user`/`broadcast_all` take a second,
genuinely-tagged `remote_except: &[NodeConnId]` parameter, merged with the
existing local `node_excepts(...)` output before the relay call. The existing
local `except` array's wire shape and cost are **untouched** — single-node
calls pass an empty `remote_except` (a shared empty `Uint32Array` on the JS
side), so this is zero-cost when unclustered, consistent with §12 rule 1
applied to the mesh.

## The cluster-only except channel (design note)

`Target.except()` (rooms.ts) now classifies a decoded socket id as local or
remote by comparing against `selfNode` (this server's own `cluster.nodeId`,
threaded into every `Target` at construction). Local excepts stay on the
existing flat `[hi, lo, …]` array; remote excepts go on a **separate**
`[node, hi, lo, …]` array. This was a deliberate two-array design rather than
widening the existing `except` array to carry a node per entry, specifically
so single-node behavior — wire shape, allocation pattern, decode cost — does
not change at all: `except_ids()` on the Rust side is byte-for-byte what it
was before this PR; `except_ids_remote()` is new code on a path that only
runs when `remote_except` is non-empty, which single-node calls never produce.

## `sendNode` — cross-node `toSocket`

`toSocket(id)` decodes the id's node segment (`ids.ts`, already
node-prefix-aware since 3D). When the decoded node differs from this server's
own `cluster.nodeId`, `Target.send()` calls the new `engine.sendNode(node, hi,
lo, data, isBinary)` instead of `send`/`sendText`. No text fast path — this is
already a relay hop, not a per-message hot path, so the SDK converts a string
to a `Buffer` first rather than adding a `sendTextNode` mirror. Same-node and
unclustered targets are unaffected (unchanged `send`/`sendText` call).

## Rules audit

- **Rule 1 — zero per-message JS added.** Cluster wiring is config-in,
  stats-out; no new JS runs per message. `remote_except`/`sendNode` are only
  reached when an app explicitly targets a remote socket — still zero JS
  *added* to the message path itself (the fan-out decision was already being
  made in `Target.send()` before this PR).
- **Rule 4 — `stats().cluster` cost is O(peers).** `cluster_summary()` is O(1)
  atomics; `cluster_peer_pressures()` is O(peers), peers ≤ 50 (RFC 0004 §8
  envelope) — stated, not measured (no compiler to benchmark with in this
  sandbox; flagged for the verifier to confirm against the existing 3A
  per-peer memory table).
- **Rule 5 — no new queues.** `remote_except`/`sendNode` reuse the mesh's
  existing bounded `PeerQueue` (3A) via `Cluster::relay_*`/`MeshNode::relay`
  — nothing new to bound.
- **Bridge constants untouched.** `TSFN_QUEUE_BOUND`, `ENGINE_BRIDGE_QUEUE_CAPACITY`,
  `BRIDGE_BATCH`/`BRIDGE_FLUSH_INTERVAL` — not touched by this PR.
- **Crypto swap: KATs prove identical outputs.** The existing FIPS 180-4 /
  RFC 4231 known-answer-vector tests in `crypto.rs` are unchanged; they now
  regression-test `hmac::Hmac<sha2::Sha256>` instead of the vendored impl. If
  they pass (pending real `cargo test -p beamsocket-mesh`), the outputs are
  byte-identical to before, which is the whole point of the swap.

## Deviations, honest

- **No compiler access — see the verification-status banner at the top.**
  This is the load-bearing deviation for this PR; every other deviation below
  is secondary to it.
- **Package-lock.json left unedited.** `package.json` (main + all 7
  `npm/*/package.json`) bumped to `0.2.0`, but `package-lock.json`'s
  registry-resolved entries for the platform packages were left at
  `0.1.0-alpha.0` on purpose: those entries carry `integrity` hashes for
  tarballs that exist on the npm registry today. Hand-editing the version
  field without a real hash would produce a lockfile that lies about what it
  can verify. The lockfile needs a real `npm install` once the 0.2.0 platform
  packages are actually published — same order of operations the existing
  publish flow already uses (platform packages first, then the main package
  resolves against them).
- **No git tag, no npm publish, no CI run.** Per the work order and an
  explicit user decision: this PR stops at code + local commits. Tag/publish
  is a follow-up once verification is green.
- **`kill -9` / clean-exit tests use real child processes** (`cluster-process.
  integration.test.mjs`), separate from the in-process 3-node tests in
  `cluster.integration.test.mjs` — you cannot `SIGKILL` a thread within your
  own test process without killing the test runner. This mirrors
  `examples/cluster` structurally but is a standalone, minimal worker
  (`helpers/cluster-worker.mjs`), not a reuse of the example, to keep the
  example's own README commands exactly what a user would actually run.
- **The "single-node zero-cost re-proven from JS" required test is not a new
  test file.** The existing `observability.integration.test.mjs`'s "PERF
  GUARD: sampler ON vs OFF" test already is the 2A-style echo-throughput/p99
  guard the work order asks for; running the **full existing JS suite green
  on the rebuilt 0.2.0 addon** (a separate required-test bullet) is what
  re-proves it against this addon specifically. Writing a second, redundant
  perf-guard test seemed like the wrong kind of thoroughness.
- **Test-file `remote_except` coverage is exercised indirectly.** The
  cross-node except test in `cluster.integration.test.mjs` drives the fix
  through the real JS→native→Engine path end to end; there is no
  Rust-level unit test added for `broadcast_room`'s new parameter in
  isolation (the existing phase3d.rs E2E gate, extended, would be the more
  rigorous place for that — left as a follow-up rather than duplicating
  coverage under time constraints).

### Bug found and fixed: cluster mode silently dropped every client message

Running the example by hand (not covered by the automated suite — see why
below) surfaced a real regression: with `cluster` configured, a client's
`socket.id` is a **three-segment** node-prefixed string (`encodeSocketId(hi,
lo, nodeId)`, e.g. `"1-0-0"`) — but `server.ts`'s internal `#sockets` map
lookups on the native bridge's `onMessage`/`onClose`/presence-metadata paths
used a **second, independent** key-builder, `socketKey(hi, lo)`, which never
had a node prefix. Under cluster config the store key (`socket.id`, 3-segment)
and the lookup key (`socketKey(hi, lo)`, 2-segment) never matched, so
`#sockets.get(...)` always missed and `?.emit('message', …)` silently no-oped
— every client-sent message vanished, and connection cleanup
(`socket._handleClose`) never ran, under cluster mode only. Single-node
`encodeSocketId(hi, lo, undefined)` happens to produce the same 2-segment
form `socketKey` always did, which is why single-node was unaffected and
every existing automated test — including `cluster.integration.test.mjs` —
missed it: that suite drives every cross-node scenario via **server-initiated**
`io.toRoom()/toUser()/toSocket().send()`, never via a client message hitting
`socket.on('message', …)`, so the broken lookup path was never exercised.
`examples/cluster/node.mjs` is the one piece of code in this whole PR that
does drive that path (`socket.on('message', (data) => { … io.toRoom(...).send(...) })`),
and it was silent-broken from the start.

**Fix** (`packages/beamsocket/src/server.ts`): deleted the duplicate
`socketKey(hi, lo)` helper; the three call sites (`onMessage`, `onClose`,
`presence()`'s metadata getter) now build the lookup key with the same
`encodeSocketId(hi, lo, this.#nodeId)` used to build `socket.id` in the first
place — single source of truth, can't drift again. Verified via a minimal
single-node-cluster repro (broken before the fix, fixed after) and a real
3-node run: cross-node chat works end-to-end, sender correctly excepted,
relay counters (`relayIn`/`relayOut`) increment as expected in every
direction.

**This was invisible to every gate in this PR's own checklist** — clippy,
cargo test, tsc, and even the from-scratch `npm test` run all stayed green
throughout, because none of them drive a client-initiated message through a
clustered server. Worth a regression test in `cluster.integration.test.mjs`
(a client `ws.send()` on a clustered server, asserting the server's
`socket.on('message', …)` fires) — not added here to keep this fix minimal;
flagged as a follow-up.
