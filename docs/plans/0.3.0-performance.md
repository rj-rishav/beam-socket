# 0.3.0 Performance Phase — Work Plan

**Status, 2026-08-20:** Tasks 1, 2, and all of Task 5 are done — 0.2.0 is
published on npm under `alpha` (see `docs/reports/0.3.0-task1-flush.md` for
the flush before/after numbers). Tasks 3 and 4 are the only work left, and
both need a physical machine, not this sandbox.

**Source:** the 2026-08-20 same-box benchmark analysis (raw data:
`benchmarks/results/*-thisbox*.json`, commit `9b7ca87`). What it found, in one
paragraph: 0.2.0 unclustered is byte-identical-in-cost to 0.1.0 (cluster wiring
is free when unused — confirmed, done, no work needed there). Against
competitors, BeamSocket loses low-concurrency echo to ws/uWS by ~2.3–2.6×, and
most of that gap at p50 is one specific, fixable thing: **the 1 ms bridge flush
timer** that every app-bound message waits out when there's no load to batch.
The rest of the gap (the FFI hop itself) is the architecture's deliberate cost
and is *not* to be "fixed" — it's what buys event-loop freedom at scale. The
plan below attacks what's actually attackable, in order.

**Ground rules — read before touching anything:**

1. Never add per-message JS. Rule 1 of `docs/ENGINEERING.md` §12. If your
   change makes JavaScript run once per message where it didn't before, stop.
2. Never add an unbounded queue. Every buffer in this codebase has a cap and a
   drop counter. Yours must too.
3. Every task below ends with the same three commands green before you commit:
   ```bash
   cargo fmt --check && cargo clippy --workspace --all-targets -- -D warnings
   cargo test --workspace
   npm test -w beamsocket        # needs: npm run build:native -w beamsocket && npm run build -w beamsocket
   ```
4. Benchmark **before AND after** on the same box in the same hour. A number
   without its "before" twin is noise, not evidence.

## Task 1 — Adaptive bridge flush (the p50 lever)

**Priority: 1. Difficulty: medium. Expected win: p50 echo latency at low
concurrency drops from ~2.2 ms toward ~1.2 ms (removes most of the 1 ms timer
wait).**

### The problem, plainly

Open `crates/node/src/bridge.rs`, find `drain_loop` (~line 305). Today it does:

1. Wait for the first event.
2. Start a 1 ms timer (`BRIDGE_FLUSH_INTERVAL`).
3. Keep collecting events until the batch holds 256 (`BRIDGE_BATCH`) **or**
   the timer fires.
4. Flush the batch to JS in one TSFN call.

Under load this is perfect — the batch fills fast and the timer never matters.
At low load (one echo in flight), the batch holds exactly 1 event and waits the
full 1 ms for company that never comes. That 1 ms is pure added latency, and
it's most of the p50 gap vs ws (2.198 ms vs 0.927 ms measured 2026-08-20).

### The change

After receiving the first event, **greedily drain whatever is already queued
with `try_recv()`, and if the channel is then empty, flush immediately —
skip the timer entirely.** Only fall into the timer+select loop when the
greedy drain shows more events are still flowing. In pseudocode:

```
loop {
    first = rx.recv().await else break;
    batch.push(first);
    // NEW: greedy drain — take everything already sitting in the channel
    while batch.len() < BRIDGE_BATCH {
        match rx.try_recv() {
            Ok(ev) => batch.push(ev),
            Err(Empty) => break,
            Err(Disconnected) => { flush(); return; }
        }
    }
    // NEW: channel drained empty and batch is small → low-load regime,
    // flush now, don't wait the timer
    if batch.len() < LOW_LOAD_THRESHOLD {   // start with 16, tune by measurement
        flush();
        continue;
    }
    // otherwise: existing timer+select fill loop, unchanged
    ...
}
```

Why the threshold instead of "flush whenever try_recv is empty": under
sustained load the producer and drain thread interleave, and try_recv can
momentarily see empty between bursts. Flushing every time it blips empty would
shatter batches and tank throughput. A small threshold ("if I only found a
handful, it's quiet — ship them") keeps both regimes correct. `16` is a
starting guess — the measurement step below is what decides it.

### Files you will touch

- `crates/node/src/bridge.rs` — `drain_loop` only. **Do not touch**
  `BRIDGE_BATCH`, `BRIDGE_FLUSH_INTERVAL`, `ENGINE_BRIDGE_QUEUE_CAPACITY`, or
  `TSFN_QUEUE_BOUND` — the constants are validated in `docs/rfcs/0001` results
  and stay as they are. You're changing *when* the timer starts mattering, not
  the bounds.

### Watch out

- The existing unit test `drain_loop_batches_by_size_and_flushes_rest_on_close`
  (bottom of `bridge.rs`) pre-loads 259 events and asserts flushes of
  `[256, 3]`. Your greedy drain still produces exactly that (channel is
  pre-filled, so try_recv never sees empty until 256 are taken). Run it first,
  make sure you understand *why* it still passes. Add a **new** test for the
  new behavior: send 3 events, assert one flush of 3 arrives in well under
  1 ms (use `tokio::time::pause` or a real-time bound of, say, 500 µs).
- Don't reorder events. The batch must stay FIFO — the greedy drain naturally
  preserves this; just don't get clever.

### How to verify (all four, in this order)

```bash
# 1. Rust tests still green + your new test
cargo test -p beamsocket-node

# 2. Rebuild the addon + SDK
npm run build:native -w beamsocket && npm run build -w beamsocket

# 3. The JS perf guard still passes (this is the throughput regression tripwire)
node --test packages/beamsocket/__tests__/observability.integration.test.mjs

# 4. The actual before/after (run BOTH before your change and after):
cd benchmarks && node driver.mjs --lib beamsocket --out results/flush-before.json
# ...make the change, rebuild...
cd benchmarks && node driver.mjs --lib beamsocket --out results/flush-after.json
```

### Definition of done

- [x] `latency.p50ms` drops by ≥ 0.5 ms vs your own same-day "before" run.
      **Done 2026-08-20: 2.193 ms → 1.025 ms (3-run avg, same box, same
      hour) — a 1.17 ms drop, well past the bar.**
- [x] `throughput.msgsPerSec` within ±10% of "before" (i.e., not regressed
      beyond the box's noise band). **Improved +89% (77,122 → 145,942
      msg/s), not a regression.**
- [x] Fan-out numbers (1k/3k/5k) within ±15% of "before". **1k improved 35%
      (15.17 ms → 9.81 ms — now beats both ws and uWS at this size); 3k
      moved +11.5% (29.83 → 33.27 ms, inside the band, high run-to-run
      variance on both sides); 5k flat (42.53 → 42.20 ms, −0.8%).**
- [x] New drain-loop unit test committed alongside the change.
      `drain_loop_low_load_flushes_immediately_without_the_timer` in

## Task 2 — Fix the idle-RSS benchmark (measurement debt)

**Priority: 2. Difficulty: easy. Expected win: trustworthy memory numbers, so
Task 3 can be judged at all.**

### The problem

The 2026-08-20 run showed the idle-memory suite swinging 5–10× between
back-to-back identical runs (423 B then −46 B per connection). 3,000
connections × 2 s settle is too small/short for allocator noise on a shared
box. You cannot evaluate Task 3's memory work with a broken ruler, so this
task comes first.

### The change — in `benchmarks/driver.mjs`

1. Raise the default: `MEM_CONNS` from `3000` → `10000`.
2. Raise the settle: the `sleep(2000)` in `measureMemory` → `sleep(8000)`.
3. Sample RSS 5 times, 1 s apart, after settle; use the **median**.
4. Print all 5 samples into the JSON (`rssSamplesKB: [...]`) so noise is
   visible instead of hidden.

### Definition of done

- [x] Three consecutive runs of
      `node driver.mjs --lib beamsocket` report `bytesPerConn` within ±25% of
      each other. **Done 2026-08-20 at the stated MEM_CONNS=10000/settle=8s
      (no need to raise further): 4797, 5375, 5272 B/conn — ±11% spread.**
      Ended up also needing two changes beyond the stated three, found while
      making the numbers actually stable: (a) `base` must be sampled the
      same way as the loaded reading (median over spaced samples, not one
      instant snapshot) — it's captured right after the fan-out suite's own
      connection churn, and a single-sample snapshot there was catching that
      suite's not-yet-collected garbage; (b) a throwaway warm-up
      open/close batch before sampling `base`, because opening the *target*
      connection count is itself enough allocation pressure to trigger a
      GC/allocator-trim pass that a `base` snapshot taken beforehand never
      benefits from — without it, `base` and `loaded` aren't measuring the
      same kind of process state and the delta is meaningless (this is what
      was producing physically-backwards negative bytesPerConn for `ws`).
- [x] Same stability check passes for `--lib ws` (its true value is small, so
      this is the sensitive canary). **Stable at −2,824 B/conn avg (±10%
      spread across 3 runs) — see `docs/reports/0.3.0-task1-flush.md` for why
      this is negative and why that's a real, reproducible finding about
      this box's allocator behavior under `ws`'s connection pattern, not
      measurement noise.**
- [x] `benchmarks/README.md` gets one added sentence noting the suite's
      minimum-N for stable numbers.

## Task 3 — Density levers (memory per connection)

**Priority: 3. Difficulty: medium-high. Do NOT start until Task 2 is merged.
Expected win: up to ~6 KB of the ~11.6 KB/conn structural budget.**

Two independent levers, documented in `benchmarks/README.md`'s memory table.
Do them as **separate PRs**, measured separately.

### 3a. Lazy codec read buffer (~4 KB/conn)

- File: `crates/core/src/transport/websocket.rs`, `READ_BUFFER_SIZE`
  (currently `4 * 1024`, passed to tungstenite's `read_buffer_size`).
- Check what the pinned tungstenite version supports first: if it can start
  smaller and grow, drop the initial to `1024` and measure. True
  allocate-on-first-frame laziness may require holding the config until the
  first read — only go there if the simple shrink shows real savings.
- Measure with the (now fixed) idle-RSS suite **and** the `--ignored`
  measurement tests in `crates/core/tests/phase1d.rs`.
- **Risk to check:** small read buffers can cost throughput on large frames.
  Run the echo throughput suite with 64 B **and** a 16 KB payload variant
  before/after. Any regression > 10% on the big payload kills the change —
  revert, document, move on.

### 3b. Lazy per-connection control channel (~part of 2.5 KB/conn)

- Files: `crates/core/src/connection/mod.rs` (the `mpsc::channel::<Control>(4)`
  + `watch` close signal), `crates/core/src/connection/registry.rs` (~line 210).
- Today every connection allocates a control channel (~200 B) + close watch
  (~150 B) at accept time, used only when the server initiates an action
  toward that specific socket (close, etc.).
- The idea: allocate on first server-initiated action instead. **This is the
  risky one** — the close path uses `try_send` with the watch as fallback, and
  a lazily-created channel introduces a race (action arrives while the channel
  is being created). Design first: write the locking story into the PR
  description *before* coding. If it needs a mutex on the hot path, **stop and
  don't do it** — Rule: never trade a hot-path cost for an idle-memory win.
- Acceptance: idle RSS drop visible in the fixed suite; zero change to
  `phase2b.rs` admin-disconnect semantics; churn test
  (`admin_disconnect_churn_leaves_registries_empty_rss_flat`) still green.

## Task 4 — The pinned-box run (release blockers for the headline claims)

**Priority: 4 in this list but schedulable in parallel — it's hardware work,
not code work. Difficulty: logistics.**

Everything in `benchmarks/REPORT.md`'s "Still owed" section. These numbers are
the reason the architecture exists, and none of them can run on the shared
sandbox. Checklist:

1. **Hardware:** one dedicated server box (the "pinned box" —
   `benchmarks/README.md` names the reference spec), plus at least one
   separate client machine on the same switch. Clients and server must not
   share cores.
2. **OS prep on the server:** raise fd limits (`ulimit -n 1048576`), bump
   `net.ipv4.ip_local_port_range` and `net.core.somaxconn`; multiple client
   IPs or multiple client machines to get past the 64k-ports-per-source limit
   at 500k connections.
3. **The four gates, in order of cost:**
   - Echo p99 < 5 ms at 10k connections (target from `benchmarks/README.md`).
   - 100k-member room fan-out < 150 ms (the ARCHITECTURE §5 gate).
   - Socket.IO comparison at 25k+ (the scale the sandbox capped out at).
   - 500k-connection density (RSS/conn at half a million idle sockets).
4. **Rules:** same driver, unmodified; 2+ passes per number; losses published
   with the wins (this repo's benchmark honesty rules are non-negotiable —
   read the top of `benchmarks/README.md` before you start).
5. Output: a dated section in `benchmarks/REPORT.md` + raw JSON in
   `benchmarks/results/`. Until this lands, README performance claims keep
   their "projection, not result" framing — do not soften that language.

## What we are explicitly NOT doing (so nobody burns a week on it)

- **Removing the FFI hop.** It's the architecture. The ~1 ms of it that's the
  flush timer is Task 1; the rest is the price of the product.
- **Chasing uWS on raw echo.** A C++ transport with no rooms/identity/
  presence/mesh will win request-response echo forever. The honest scorecard
  in `benchmarks/REPORT.md` already says this in print.
- **Touching the bridge bounds** (`BRIDGE_BATCH`, queue capacities). Validated
  under RFC 0001; changing them re-opens the overload-survival proofs.
- **A `sendTextNode` fast path.** Cross-node sends are already a relay hop;
  the string→Buffer copy is noise there (per the 0.2.0 PR design notes).
